我们之前为 QimenLLM 确定的训练方案，核心不是把《神奇之门》全文直接丢给大模型，让它背诵案例，而是：
让大模型学习张志春等作者如何运用奇门知识、如何选用神、如何分析九宫盘、如何综合证据、如何判断结果和应期。
与此同时，排盘计算、固定知识、规则适用条件和事实校验，应当由独立程序与数据库负责。
这套方案已经写进你的 GitHub 项目最高指令：
QimenLLM — Codex Master Specification
我按照我们原来的 Prompt，把整个训练方案重新梳理一下。
一、我们最终到底要训练出什么模型？
我们的目标不是普通的奇门排盘软件，也不是把古籍放进 ChatGPT，让它搜索后回答。
最终的 QimenLLM 应该像一个经过专业训练的奇门研究者。
例如，普通用户问：
我昨天丢了一个钱包，里面有身份证和现金。你帮我看看还能不能找到？

QimenLLM 应该能够：
1. 理解这是钱物丢失问题。
2. 确定应该使用什么起盘时间。
3. 调用独立程序生成奇门九宫盘。
4. 从《神奇之门》检索钱物丢失的相关规则。
5. 根据实际条件选择日干、时干等用神。
6. 判断失主宫与失物宫之间的生克关系。
7. 检查玄武、天蓬、空亡、入墓、反吟等信息是否适用。
8. 综合有利、不利证据，形成传统奇门判断。
9. 根据适用条件判断应期。
10. 用自然中文解释判断过程，并列出古籍出处。
整个过程不能只套固定模板。
例如，不能机械地认为：
“时干临玄武，所以肯定是被偷了。”
原书明确提到玄武也可能表示自己忘记，因此模型必须考虑其他证据。
我们训练的重点，就是这种有条件、多证据的综合判断能力。
二、最重要的设计：大模型、排盘引擎、知识库各自负责什么？
我们明确规定采用三个核心部分。
1. 确定性起盘引擎
排盘不应该由大语言模型凭记忆完成。
程序负责计算节气、干支、阴阳遁、局数、旬首、值符、值使、九宫、天地盘、八门、九星、八神、空亡、马星等内容。
不同起局方法，例如拆补法与置闰法，需要明确区分，不能随意混用。
程序计算出的九宫盘，就是之后所有分析使用的同一张盘。
这部分追求的是确定性计算正确率，而不是让 LoRA 去记忆。
2. 专业知识数据库
数据库负责保存：
- 古籍基础知识与固定属性。
- 用神选择规则及适用条件。
- 九宫、门、星、神、天干、五行等关系。
- 具体断案方法和应期方法。
- 原书完整案例、分析、预测和反馈。
- 不同作者、古籍及起局方法之间的分歧。
例如，用户问自己找工作与问父亲找工作，虽然属于同一大类，但不一定使用完全相同的用神。
数据库必须先判断规则是否适用，不能只根据关键词搜索几段文字就交给模型自由发挥。
3. 专业微调的大语言模型
这才是我们真正需要训练的部分。
模型需要学习的是：
如何理解问题 → 如何选择适用规则 → 如何分析盘面证据 → 如何进行专业综合判断 → 如何解释给用户。
因此最终系统不是只有一个 LoRA 模型，而是：
确定性起盘引擎 + 专业知识数据库 + 条件规则系统 + 微调后的大语言模型 + 事实验证器。
三、我们怎么使用你现在整理的《神奇之门》？
这是我们整个训练计划最关键的一步。
你目前逐章整理的内容会分成两大训练来源。
第一类：基础知识
包括阴阳五行、天干地支、九宫、八门、九星、八神、旺衰、格局、用神以及应期等。
这些内容既要进入专业知识数据库，也可以生成适合模型学习的监督任务。
例如，原书《钱物丢失预测》说：
钱物丢失，一般以日干落宫为失主，以时干落宫为丢失之钱物。

我们不是只让模型记住这句话。
我们还要让模型学会：在什么问事条件下使用这条规则，如何绑定日干和时干，如何根据落宫关系分析，以及什么情况下信息不足。
如果原书同时给出多种判断方法，模型需要知道它们的区别，而不是默认每种方法都同时适用。
第二类：真实历史案例
这是我们训练专业断案能力的核心数据。
例如，《钱物丢失预测》中有一个案例：
1996年3月，一位妇女发现放在家里的6800元人民币不见了，怀疑是不是侄儿拿走了。
作者起盘后，根据日干、时干、玄武和甲子戊等信息，判断钱没有被偷，而是失主自己移动了位置、后来忘记了。
最终，钱确实在家中立柜里的床单中找到。
对于这样的案例，我们不能简单生成一个训练问答：
问：6800元是谁拿走的？
答：没有被偷，是失主自己放进床单后忘记了。

这样训练出来的模型只会背答案。
我们真正要做的是将完整案例保留下来，再从中生成不同专业任务。
例如：
任务A：用神选择
输入：当事人丢失现金，询问能否找到，提供完整问事背景。
训练目标：选择该问事适用的用神，并引用原书规则。
任务B：盘面分析
输入：问事背景、已确定的用神以及完整九宫盘。
训练目标：找出与失物相关的宫位、门星神和生克关系。
任务C：综合证据
输入：作者预测当时已经掌握的背景和盘面证据。
训练目标：按照作者的判断方法，综合支持与反对某一结论的证据。
任务D：应期分析
输入：原书实际使用的应期规则和对应盘面信息。
训练目标：说明应期从何而来、使用了什么条件，而不是凭空给出日期。
任务E：多轮反馈
输入：原始问题、已经作出的分析，以及用户后来新增的信息。
训练目标：根据新增信息继续分析，而不是每次都重新起盘或重复最初答案。
同一个完整历史案例可以产生多个不同训练任务，但它们必须保留同一事件来源，不能人为拆散成互不相关的案例。
四、我们特别强调：不能让模型提前知道结果
这是我们原 Prompt 中非常严格的一项要求。
比如刚才那个6800元案例，作者在第一次判断时不知道钱后来会从床单中掉出来。
所以训练初次断案任务时，模型的输入中绝对不能包含这个最终结果。
数据必须区分四个时间阶段：
第一阶段：预测前已知信息。 当事人已经告诉作者什么，问事背景是什么，哪些信息确实已知。
第二阶段：作者当时的预测。 作者选择了什么用神、使用什么盘面证据、作出了什么判断。
第三阶段：事后反馈。 后来找到钱了吗？在哪里找到？实际发生了什么？
第四阶段：反馈后的分析。 作者是否根据后来的结果重新解释盘面、修正判断或补充应期。
训练首次预测时，只能使用第一阶段可知信息以及当时确实可获得的盘面和规则。
第三、第四阶段的信息不能提前进入输入。
这对你现在整理的古籍尤其重要，因为不少案例存在作者事后补充分析的情况。
如果我们不做这种隔离，模型的测试成绩可能非常高，但实际上只是提前看到了答案。
五、具体使用什么模型、什么训练方法？
我们当时决定：
不从零训练一个 GPT，而是选择已有的中文开源基础模型，通过 SFT 和 LoRA/QLoRA 实现专业微调。
原因是《神奇之门》和未来约20本古籍的数据规模，不足以支持从零预训练大型通用语言模型。
我们希望保留基础模型已经具有的中文理解、通用推理和自然语言表达能力，只针对专业奇门任务进行训练。
基础模型
原 Prompt 建议首先评估 Qwen 等适合中文任务的开放权重模型。
考虑到你的家庭计算机有一张 RTX 4090，24GB 显存，初步优先评估大约 7B～9B 参数规模的模型。
但没有提前锁定具体型号。
必须实际测试显存、上下文长度、训练速度、输出质量、微调稳定性及模型使用许可，再确定最终方案。
训练方式
首先使用 Supervised Fine-Tuning（SFT，监督微调）。
简单说，就是让模型看到高质量的专业任务输入，并学习如何生成正确、有依据的专业分析。
然后优先考虑使用 LoRA 或 QLoRA，而不是一开始就全参数微调。
这可以更合理地利用你的4090显存。
我们的 Prompt 还特别强调：
LoRA 不是用来背九宫五行或记住历史案例结局，而是用来学习专业分析步骤、证据组织、类象适用条件、应期判断和自然语言表达。
没有高质量偏好数据前，也不急着使用强化学习或偏好优化。
六、正式训练之前，我们必须先做五组对照实验
这是我们原 Prompt 规定的训练研究方法。
不能上来直接微调，然后看到 Loss 下降就认为模型进步了。
我们需要在同一套测试题上比较：
实验组	模型能够使用什么
A	原始基础模型
B	基础模型 + 确定性九宫盘
C	基础模型 + 九宫盘 + 古籍知识检索
D	基础模型 + 九宫盘 + 条件化专业规则
E	以上完整系统 + SFT/LoRA 微调模型


这能够回答一个非常重要的问题：
模型专业能力的提升，究竟来自可靠的工具和知识检索，还是来自真正的参数微调？
假设某项专业分析测试中，D组已经表现得很好，而E组微调后反而降低了专业正确率，那么我们就不能说微调成功。
训练必须产生能够重复验证的专业提升。
七、怎么划分训练集、验证集、盲测集？
我们明确规定：按照完整事件家族划分，而不是随机打散问题和答案。
假设同一个历史案例产生了20条训练任务。
这20条任务必须全部属于同一个数据分组。
不能出现其中15条用于训练，另外5条用于测试。
否则模型可能已经通过训练任务认识了这个案例，再做测试就不算真正的盲测。
同样，如果《神奇之门》与附录，或者未来《开悟之门》重复讲述同一个历史事件，它们也必须归入同一个事件家族。
训练、验证和测试三个集合之间不能发生这种泄漏。
我们还要求建立另一套真正独立的未见案例测试集。
其中的案例、盘面和问事背景不能出现在训练中。
最终评估至少要判断：
模型能否在没有提前见过案例结局的情况下，正确选择用神、分析证据、判断应期，并作出符合原书方法的合理解释。
八、我们如何判定模型真的学会了？
原 Prompt 明确要求六层测试。
测试层级	重点
第一层	古籍原文、案例、盘面、出处和数据库完整性
第二层	五行、干支、门星神、九宫等基础事实
第三层	独立起盘及完整九宫正确性
第四层	具体问事的用神选择是否正确
第五层	综合断案、证据取舍、应期和反馈续断
第六层	全新日期、全新盘面、自然语言问事及实际产品能力


这里有两个特别重要的要求。
第一，模型不能把基础知识错误包装成流畅回答。
例如，如果一个宫位实际没有天心星，模型却说那个宫位有天心星，程序应当识别为错误并阻断。
第二，拒绝回答不等于回答正确。
假设100道题中，模型只回答20道，其中18道正确，另外80道因为无法处理而拒答。
不能只报告“90%正确率”。
必须同时报告实际完成了多少题，以及完成题目的专业正确性。
另外，原书作者所称的70%～80%准确率，是作者的经验主张，不是 QimenLLM 已经取得的统计成绩。
我们未来真正的现实预测准确率，还需要单独记录事前预测及后续结果，不能用历史案例复现率代替。
九、训练完成之后，用户问事时怎么运行？
最终正式执行链只有一条：
用户自然语言提问
↓
识别具体问题和人物关系
↓
确认缺失的必要条件
↓
确定性起盘
↓
查询古籍知识数据库
↓
判断规则适用条件
↓
绑定用神
↓
提取盘面事实与相关证据
↓
调用已经微调的专业模型进行综合分析
↓
程序验证宫位、规则、证据与来源
↓
生成最终自然语言回答
↓
支持用户追加信息和继续分析
特别注意：模型不是每次问事都重新训练。
训练是离线进行的，问事是运行已经训练好的模型，并实时调用起盘引擎和知识数据库。
未来增加新的古籍时，可以先更新知识库，使模型能够检索新资料，再通过版本化的数据集定期微调和比较模型。
十、我们的两台电脑如何分工？
这也是原 Prompt 已经明确规定的。
MacBook Air M2，24GB 内存主要负责 Codex 开发、古籍整理、知识入库、测试、数据集生成，以及远程管理训练。
家庭 RTX 4090，24GB 显存主要负责基础模型测试、SFT/QLoRA训练、模型对照实验、推理性能测试及训练检查点保存。
我们要求训练过程必须保存模型版本、数据版本、LoRA配置、学习率、批次、训练步数、显存使用、损失曲线、测试结果和检查点。
这样未来更换模型或者增加古籍，都能够重复之前的实验。
