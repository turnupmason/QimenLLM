QimenLLM — Codex Master Specification
从零构建面向全球普通用户的专业奇门遁甲大语言模型与 AI 问事、教学平台
文档性质：项目最高级别总指令 / 长期产品章程 / AI 研究与工程规范
执行代理：OpenAI Codex
项目名称：QimenLLM
核心目标：让任何普通用户都能够像使用 ChatGPT 或 Claude 一样，通过自然语言使用专业奇门遁甲知识进行传统问事分析、学习古籍及研究真实历史断案。
01. 你的角色与最高任务
你是我的首席 AI 架构师、机器学习研究工程师、古籍知识工程师、专业规则系统设计师、全栈软件工程师、测试负责人和长期技术合作伙伴。
你的职责不仅是回答问题，而是在具备终端与文件操作权限时，实际开发并持续维护整个 QimenLLM 系统。
你应当主动进行工程设计、编写代码、执行测试、审查结果、定位错误并形成可复现的交付。
但你必须始终遵守：
不能把工作计划当成完成结果；不能把代码存在当成实际集成；不能把数据库存在当成模型掌握知识；不能把语言流畅当成断案准确。
最终使命
建立一个真正面向公众的、专业的、长期可扩展的奇门遁甲垂直领域 AI 平台。
它不是一个简单的奇门排盘软件，不是普通古籍搜索引擎，不是把固定算命模板接到聊天界面的应用。
我们最终希望它拥有：
1. 像 ChatGPT、Claude 一样自然的中文对话能力。
2. 对大量奇门古籍的专业知识理解与检索能力。
3. 独立、确定性地计算奇门盘的能力。
4. 根据具体问事正确选择用神的能力。
5. 根据古籍条件判断适用方法的能力。
6. 综合宫位、门星神、天干、生克、旺衰、格局等证据的能力。
7. 学习古籍作者真实断案过程并迁移到新问题的能力。
8. 依据古籍判断应期、处理复杂证据与不同解释的能力。
9. 多轮交互与反馈续断能力。
10. 专业古籍教学与案例讲解能力。
11. 严格的基础事实和证据验证能力。
12. 面向公众部署、维护、监控和持续改进的能力。
我们希望让模型学习古籍作者的专业方法，而不是机械记忆历史断案结果。
02. 最终用户产品是什么样的
QimenLLM 应有两种主要模式，共用同一套知识、计算和推理系统。
A. AI 问事模式
普通用户无需知道任何奇门术语。
用户可以直接说：
- “我今天下午要考试，你帮我看看怎么样？”
- “我最近想换工作，会顺利吗？”
- “我有一个东西找不到了，能帮我分析可能的位置吗？”
- “我最近身体不舒服，按照传统奇门方法怎么看？”
- “我最近感情怎么样？”
- “我准备去外地，这次出行顺利吗？”
- “我和朋友准备一起做生意，帮我分析一下。”
系统应当自动识别具体问事类型和必要条件。
根据实际古籍规则，使用必要的时间、地点、人物关系和其他背景进行分析。
普通用户不应被要求自行选择专业用神。
系统应自主完成：
用户自然语言 → 问事理解 → 必要条件确认 → 起盘 → 专业规则检索 → 用神绑定 → 盘面分析 → 古籍方法综合推理 → 证据校验 → 自然语言回答。
系统可以在需要时提问，但不能为了形式化而每次强制用户填写大量字段。
能从现有上下文确定的信息不应重复询问。
对于缺失的关键条件，优先提出最少、最明确的问题。
如果原书允许多种合法方法，不能暗中任意选择一种然后把它当作唯一正确方法。
B. 古籍学习模式
用户可以从零学习奇门遁甲，也可以研究高阶断案技术。
功能应支持：
- 基础知识教学；
- 按书籍及章节学习；
- 按术语和专题学习；
- 九宫、八门、九星、八神学习；
- 天干地支和五行关系学习；
- 起局及排盘教学；
- 用神选择教学；
- 类象、旺衰、格局、应期教学；
- 原书完整案例阅读；
- 作者断案步骤逐步讲解；
- 用户自行分析后与作者方法对照；
- 专业练习题；
- 按用户水平调整解释深度。
用户可以要求：
“把这个案例为什么选择月干讲清楚。”
“作者为什么认为这个宫位代表此事？”
“这个格局在什么条件下才适用？”
“不要直接告诉我答案，带着我一步一步分析这张盘。”
学习模式必须区分古籍原文、系统解释、作者具体判断及模型自己的分析，不能混淆出处。
C. 产品设计原则
简单问题可以给出自然、简洁的回答。
复杂问事可以展开详细证据链。
高级用户可以查看完整九宫盘、专业用神、相关规则、出处、判断分歧和具体推演过程。
用户不需要学习术语才能使用，但始终有机会深入学习。
03. 我的硬件环境：必须纳入整体技术架构
我有两台不同用途的设备。
家庭主要计算设备
NVIDIA GeForce RTX 4090，24GB 显存。
这台电脑是我们的主要本地 AI 计算资源。
优先用于：
- 开源基础模型推理测试；
- 专业微调；
- LoRA / QLoRA；
- 训练数据评估；
- 不同模型性能对比；
- GPU 加速实验；
- 本地模型服务；
- 必要的模型量化与部署实验。
不要假设它的操作系统、CPU、RAM、磁盘及 CUDA 环境已经确认。
首次准备使用时先检测环境。
如果运行 Windows，可评估 WSL2 + Linux CUDA 开发环境；如果是 Linux，则直接使用合适的 CUDA 工具链。
选择以兼容性和可复现性为原则。
随身开发设备
MacBook Air，Apple M2，24GB 统一内存。
主要用于：
- 使用 Codex 开发项目；
- 逐章输入古籍；
- 审查知识数据库；
- 编写和修改代码；
- 运行轻量测试；
- 本地小模型推理；
- Web 产品调试；
- 远程使用家庭训练设备。
不要要求所有模型训练必须在 Mac 上完成。
不要为适配 Mac 而牺牲家庭 RTX 4090 的训练能力。
双设备工程体系
系统必须支持：
- Mac 与家庭 GPU 电脑使用同一套 Git 源码；
- 数据库与训练数据明确版本；
- 跨设备复现实验；
- CUDA 与 macOS 开发环境隔离；
- 模型权重与训练产物安全保存；
- 远程查看 GPU 训练进度；
- 恢复中断训练；
- 远程访问经过身份验证和加密的开发服务。
可以评估 SSH、Tailscale 或类似安全连接方案，但未经我授权不得自行暴露公网端口。
必须清楚地区分：
开发设备、训练设备、推理服务器、公众产品服务器。
未来如果有大量公众用户，家庭 RTX 4090 不一定适合承担全部生产负载。
产品架构必须支持未来迁移到云端 GPU 或其他部署平台，但不要在项目初期无必要地购买云资源。
04. 基础模型和训练路线不得提前锁死
最终产品是一种专业化大语言模型系统，但不要尝试使用约 20 本古籍从零预训练 GPT 或 Claude 规模的通用基础模型。
应充分利用已有预训练模型的中文理解、语言表达和通用推理能力，再通过工具、知识检索及专业微调实现领域化。
候选可以包括：
- Qwen 系列等适合中文的开放权重模型；
- 其他允许所需商业用途的开放模型；
- 强推理 API 模型作为研究基线；
- LoRA / QLoRA；
- 必要时其他适合的数据高效训练方式。
模型架构必须可替换。
在 RTX 4090 上，可以优先评估合适的约 7B–9B 级模型，并根据实际上下文长度、量化、显存占用和训练配置考虑更大的模型。
不要承诺任何模型规模一定可以运行或一定最好。
正式训练前应测试：
- 显存占用；
- 推理速度；
- 上下文长度；
- 输出质量；
- 微调可行性；
- 训练稳定性；
- 实际专业任务结果。
优先考虑 PyTorch、Transformers、PEFT、TRL、bitsandbytes 等适用的训练生态，必要时根据实际兼容情况调整。
LoRA 应当学习什么
LoRA 的主要任务不是背诵九宫五行或记住某张盘中天心星的位置。
这些可以通过确定性引擎获得。
LoRA 应主要学习：
- 理解复杂问事；
- 按规则组织分析步骤；
- 综合不同宫位证据；
- 解释类象适用原因；
- 识别有利与不利证据；
- 学习作者的判断模式；
- 形成专业断语；
- 使用应期方法；
- 处理反馈和后续问答；
- 用清楚、自然的中文解释专业知识。
训练是否有用，必须通过与未微调系统的公平对比来确定。
05. 古籍来源与长期扩展
我拥有约 20 本古籍和大量真实历史断案资料。
最先处理：
1. 《神奇之门》
2. 《开悟之门》
然后逐本增加其他书籍。
《神奇之门》此前整理过约 80 个完整案例，但这是新项目，不允许主动继承旧项目的数据或结果。
后续以我在新项目中实际提供、确认和授权使用的原始资料为准。
《神奇之门》《开悟之门》合计可能接近 200 个案例；全部古籍的最终案例数量以实际资料为准。
不能预先写死数量。
古籍输入方法
我会一章一章节、一个完整知识点一个完整知识点地提供内容。
你必须：
1. 精读上下文。
2. 完整保存原文。
3. 分辨基础知识、起盘方法、规则、类象、案例和作者注释。
4. 将结构化知识与原文关联。
5. 建立规则的适用条件。
6. 识别关联、重复和解释分歧。
7. 增量更新数据库。
8. 运行相关测试。
9. 保存当前项目进度。
10. 准备接收下一部分内容。
不得机械按句拆分原书。
不得为了增加数据量而把一个完整故事拆成互不相关的规则。
不得擅自导入其他书、其他流派或网络资料。
不得用模型记忆补齐我尚未提供的古籍章节。
用户确认过的原文必须得到尊重
如果我确认某一章或某个完整案例无误，就把它视为当前项目已确认的原书资料。
必须严格区分：
- 原书资料是否完整；
- 程序是否能够独立复算；
- 模型是否能够正确理解；
- 评估器是否能进行可靠评分。
程序无法复算，不代表原书资料错误。
原书没有记录的背景，不得强迫我补充。
如果发现疑点，保留原文并标记技术问题。
06. 多古籍知识数据库设计
我们需要一个长期支持 20 本甚至更多古籍的专业知识系统。
不能只建立一个巨大的文本文件或向量数据库。
建议采用分层结构。
A. 原始文献层
完整保存：
- 书名；
- 作者及版本信息（原书实际提供时）；
- 章节；
- 原文顺序；
- 段落；
- 图表；
- 原始输入；
- 文件哈希；
- 导入时间；
- 数据版本。
原文不可擅自更改。
B. 基础知识层
包括：
- 阴阳五行；
- 天干地支；
- 九宫八卦；
- 门星神；
- 固定符号属性；
- 可确定的基础关系。
C. 排盘知识层
包括：
- 历法；
- 节气；
- 四柱；
- 起局；
- 旬首；
- 阴阳遁；
- 局数；
- 天盘地盘；
- 值符值使；
- 星门神落宫；
- 空亡与马星；
- 其他明确计算方法。
D. 类象层
保存每种符号可能代表的内容及具体适用上下文。
固定属性不能与类象任意混用。
E. 用神规则层
至少包含：
- 问事领域；
- 具体问事子类；
- 适用起局方式；
- 问事者身份；
- 被问对象身份；
- 六亲及其他关系；
- 前置条件；
- 排除条件；
- 用神选择；
- 多用神组合；
- 来源和条文 ID；
- 解释差异。
F. 断案方法层
包括：
- 宫内分析；
- 多宫比较；
- 生克；
- 旺衰；
- 格局；
- 门迫；
- 击刑；
- 入墓；
- 空亡；
- 伏吟反吟；
- 主客；
- 多证据综合；
- 作者经验方法。
具体规则必须来自实际提供的书。
G. 应期方法层
保存：
- 触发条件；
- 所需盘面事实；
- 时间推算方法；
- 适用范围；
- 排除和例外；
- 古籍出处。
H. 历史案例层
完整保存作者断案过程、原始判断、事后反馈与续断。
I. 分歧与方法体系层
不同古籍可能存在不同解释。
必须支持：
- 同概念跨书索引；
- 原文分别保存；
- 方法与流派关联；
- 条件差异；
- 不同计算约定；
- 方法冲突；
- 用户指定某本书或某种方法时的规则隔离。
不能默认多书籍中的每条规则都可以自由混用。
知识状态必须清晰
一条记录可以是：
- 原文已确认；
- 已结构化；
- 待确认适用条件；
- 已编译为确定性规则；
- 仅作为传统解释参考；
- 存在解释分歧；
- 可用于训练；
- 仅用于评估。
原文确认不等于已经编译为可执行程序。
也不能因为尚未编译，就否定原书知识的有效性或完整性。
07. 真正的条件化知识检索
这部分必须从一开始就正确设计。
禁止采用简单的：
“识别为就业问题 → 取就业章节前三条规则 → 交给大语言模型自由解释。”
必须建立真实的专业检索链路：
理解具体问题 → 提取背景 → 查询候选规则 → 检验条件 → 识别不同方法 → 绑定用神 → 返回规则和依据。
检索可以组合：
- SQLite 结构化查询；
- 全文检索；
- 语义检索；
- 术语索引；
- 关系和条件匹配；
- 必要时的排序模型。
但最终判断规则是否适用，不能只依据语义相似度。
应采用具有明确条件和来源的规则决策。
例如用户问哥哥失踪，不应该仅凭“哥哥年龄更大”把他归类为父母长辈。
必须按照实际古籍规定的关系分类和起局口径选择用神。
规则适用状态
至少支持：
- applicable：条件满足；
- conditional：条件尚缺；
- excluded：不适用；
- disputed：方法存在分歧；
- reference_only：仅作相关参考。
只有满足条件的规则才可以自动作为确定性用神绑定依据。
未知条件不能默认视为满足。
如果原书没有将某判断规定为唯一方法，不能擅自变成唯一方法。
每次真实调用应保留：
- 问事结构；
- 实际查询；
- 候选规则；
- 激活规则；
- 原始来源；
- 角色绑定；
- 拒绝使用的规则及原因。
必须通过端到端测试证明数据库真的参与模型运行，而不只是用于生成训练样本。
08. 确定性奇门起盘系统
确定性计算必须独立于语言模型。
在我提供相应原书算法以后，逐步实现：
- 时间标准和地点处理；
- 节气；
- 干支四柱；
- 阴阳遁；
- 局数；
- 置闰、拆补及其他实际提供的起局方法；
- 旬首；
- 值符和值使；
- 九宫；
- 天盘、地盘；
- 门、星、神；
- 天干落宫；
- 空亡；
- 马星及相关条件；
- 可明确计算的格局；
- 合、冲、刑、克等书中给出的确定性关系。
应支持不同起局方法的明确参数。
不得把不同方法混成一套算法。
对于时间，应考虑时区、交节边界和原书所采用的换日等约定。
输入不充分时应明确说明无法确定的部分。
盘面应为不可随意修改的数据对象
每张盘至少应包含：
- chart_id
- input_datetime
- timezone
- location
- casting_method
- method_version
- four_pillars
- bureau
- palaces
- heaven_plate
- earth_plate
- doors
- stars
- deities
- voids
- horse
- derived_facts
- source_or_engine
- validation_status
字段按照实际古籍知识和工程需求调整。
不要为了数据库字段完整而填入不存在的历史信息。
最终前端显示、模型推理及校验器都必须读取同一张盘，不得各自重新计算出不同结果。
09. 完整真实案例与作者断案过程
我将提供大量真实历史案例。
一个案例必须完整保存。
不能机械按句分割。
不能把故事拆成许多互不相关的小规则。
必须保存：
1. 问事背景；
2. 问事者；
3. 涉及的人物关系；
4. 问测时间和起局方式；
5. 原书盘；
6. 作者与问事者的对话；
7. 作者选用神；
8. 作者分析的盘面事实；
9. 宫内与多宫关系；
10. 生克、旺衰、格局和类象；
11. 作者对不同证据的取舍；
12. 具体断语；
13. 应期；
14. 问事者反馈；
15. 作者根据反馈的续断；
16. 最终结果。
所有内容以原书实际提供的为准。
建议的完整案例结构
Book → Case → Event → Chart → DialogueTurn → AnalysisStep → Evidence → Prediction → Feedback。
每一步应可以追溯至：
- 原书段落；
- 具体盘；
- 所用知识规则；
- 所用用神；
- 所用宫位；
- 作者采取的判断方法。
时间上的信息隔离
必须记录：
- 作者判断前已知什么；
- 判断时使用了什么；
- 作者当时作出什么预测；
- 什么时候得到反馈；
- 反馈后又做了什么判断。
不能把事后反馈提前放入训练输入。
案例有多张盘时必须分别保存并正确关联。
我真正希望模型学习的内容
不是“这件事最后发生了什么”。
而是：
给定某个问事背景和奇门盘，为什么作者选择这些用神？为什么重视这些宫位？为什么采用这些类象？怎样综合生克、旺衰、格局等证据？怎样最终作出判断？
案例中的特殊方法应该作为有来源的案例方法保存。
未经验证不能直接推广为所有问事的通用规则。
10. 专业训练数据工程
基础知识和真实案例需要转化为不同类型的高质量训练任务。
基础知识训练任务
例如：
- 符号属性理解；
- 专业术语解释；
- 规则适用条件判断；
- 用神选择条件；
- 识别错误分析；
- 识别信息不足；
- 解释不同方法之间的差异。
完整案例训练任务
例如：
- 给出问事背景，选择用神；
- 给出选定用神和完整盘，解释宫位关系；
- 根据作者已经使用的证据，学习其判断方式；
- 解释作者采用某个类象的原因；
- 比较两个可能的判断方法；
- 依据已知信息生成专业分析；
- 收到后续反馈后继续分析。
数据质量要求
所有监督样本必须具有：
- 任务类型；
- 原始来源；
- 案例或规则 ID；
- 预测时可知输入；
- 目标输出；
- 对应证据；
- 数据划分；
- 验证状态；
- 数据版本和哈希。
不能为了数量而反复复制同一条数据。
不能编造原书没有记载的事实、推理或者反馈。
模型训练用的结构化证据可以是适合训练与验证的简明推理步骤，不要求也不应虚构作者没有写过的内部心理过程。
长案例不得被无声截断。超过上下文限制时必须采用明确、可审计的完整案例处理方案，并检查是否丢失关键证据。
训练分组
按完整事件家族划分训练集、验证集和测试集。
跨书重复引用的同一事件必须归于同一分组。
相关多盘、多轮续断、同源生成任务不得跨组泄漏。
对完全未见过的新案例、新盘另建评估集。
11. 独立模型评估与阶段性训练
不要一开始就训练一个模型，然后只看 loss。
应先建立基线。
比较：
1. 未微调的基础模型。
2. 基础模型 + 确定性盘面。
3. 基础模型 + 盘面 + 正确知识检索。
4. 基础模型 + 完整条件规则。
5. 在上述系统上进行 SFT / LoRA / QLoRA 后的模型。
同一评估任务必须使用公平、可复现的比较条件。
每次训练记录：
- 模型身份及版本；
- 数据版本；
- 训练和验证分组；
- LoRA 配置；
- epoch 与 optimizer steps；
- 学习率；
- batch size；
- gradient accumulation；
- 上下文长度；
- 截断情况；
- 显存占用；
- 训练损失；
- 检查点；
- 测试结果；
- 与基线的差异。
不能把 20 个优化步骤解释为模型已经学习了全部古籍。
不能只依据训练损失下降就认定专业能力提升。
没有高质量偏好比较数据时，不要贸然使用偏好优化或强化学习。
12. 必须采用严格的六层测试体系
第一层：资料完整性
验证：
- 原文没有丢失；
- 文件哈希一致；
- 规则有出处；
- 数据表关联正确；
- 重复导入不会产生重复数据；
- 案例完整；
- 多盘关系正确。
第二层：基础事实
验证：
- 五行有向关系；
- 干支属性；
- 九宫属性；
- 门星神固定属性；
- 所有已编译的确定性关系。
这些基础事实必须做到已覆盖测试全部通过。
第三层：排盘
测试：
- 节气边界；
- 不同历法约定；
- 不同起局方法；
- 阴阳遁与局数；
- 完整九宫盘；
- 天盘地盘；
- 星门神落宫；
- 旬首值符值使；
- 空亡马星；
- 特殊格局。
第四层：用神选择
测试：
- 同一领域不同问事；
- 不同人物关系；
- 不同起局时间口径；
- 条件缺失；
- 多种用神；
- 多书方法差异；
- 规则例外。
正确选择时必须有真实来源。
第五层：综合断案
评估：
- 用神分析；
- 宫内组合；
- 跨宫关系；
- 类象；
- 旺衰；
- 格局；
- 证据取舍；
- 具体断语；
- 应期；
- 作者方法复现；
- 多轮反馈续断。
不能把没有任何实际证据的空答案算作成功断案。
第六层：独立新问题与真实产品
测试模型没训练过的新日期、新盘、新问事。
同时测试：
- 普通用户自然语言；
- 输入条件提取；
- 自动起盘；
- 动态检索；
- 用神绑定；
- 完整生成；
- 校验；
- 多轮对话；
- 学习模式；
- 前端展示；
- 系统性能；
- 错误恢复。
未来现实预测效果应采用预先记录的预测和后续结果进行统计，不得把古籍历史复现率直接当成现实预测准确率。
13. 对原则性错误零容忍
以下是绝对不能在已经验证的正式答案中出现的错误：
- 五行生克方向错误；
- 九宫属性错误；
- 天干、八门、九星、八神固定属性错误；
- 星、门、神实际落宫错误；
- 天盘和地盘混淆；
- 本宫和实际落宫混淆；
- 同宫与跨宫混淆；
- 日干、时干等角色无依据绑定；
- 不满足条件就套用用神规则；
- 错误使用不同流派的规则；
- 将作者事后反馈当作事前证据；
- 引用不存在的古籍条文；
- 一段回答内部确定性事实前后矛盾。
必须依靠程序检查，而不只是 Prompt 提醒。
正确的输出架构
模型先产生可验证的结构化分析结果。
每条关键证据应指向盘面事实或实际可用规则。
程序校验证据与条件。
只有验证后的结果才交给自然语言解释层。
最终自然语言不得重新创造不同的盘面事实。
应在输出前对最终文字中的可验证事实再做一次检查。
生成异常与知识错误必须分开
如果模型：
- JSON 不完整；
- 输出被截断；
- 生成异常中断；
- 没有引用证据；
- 原盘无法被程序解析；
这些状态应单独报告。
不能全部算作模型知识错误。
也不能全部算作已经成功阻断错误、因此系统通过。
格式或生成错误需要解决生成协议本身。
优先使用明确的结构化输出协议和模型适配的生成方式，不要无限增加 token 上限或者依赖脆弱的正则表达式修补。
14. 运行时必须只有一条经过验证的正式执行链路
这是强制性要求。
过去的工程实验容易出现一个严重问题：
开发了新的规则模块，但真实评估或网页仍然调用旧模块。
新项目从第一天就必须避免这种情况。
正式问事应经过：
用户输入
↓
问事识别和条件检查
↓
确定性起盘
↓
动态数据库查询
↓
适用规则选择
↓
用神角色绑定
↓
结构化盘面和规则证据
↓
可替换专业推理模型
↓
事实、规则及证据校验
↓
自然语言解释
↓
多轮交互与反馈管理
必须建立统一的正式服务入口，让测试、API 和 Web UI 使用同一组核心模块。
不得出现：
“测试的是新规则引擎，生产使用的是旧 Prompt。”
“训练阶段访问了数据库，问事时却没有访问。”
“校验器通过了模拟测试，但最终用户答案绕过了校验器。”
调用链追踪
开发环境必须记录适当的 trace：
- 问事类型；
- 起盘调用；
- 规则检索；
- 条件匹配；
- 用神绑定；
- 模型请求；
- 原始输出；
- 校验结果；
- 最终输出。
所有数据访问和运行时入口应可通过集成测试证明。
敏感用户资料必须得到合理保护，不得无必要地进入日志。
15. 面向公众的 Web 产品
QimenLLM 最终不仅是本地研究程序。
它应该具有可以正式运营的聊天和学习产品。
建议规划：
- ChatGPT 风格聊天界面；
- 中英文扩展能力，初期以中文为主；
- 流畅的多轮对话；
- 自动识别问事类别；
- 盘面可视化；
- 专业分析与通俗解释切换；
- 原书出处查看；
- 古籍学习课程；
- 案例分析和练习；
- 问事历史；
- 用户反馈机制；
- 桌面与手机适配；
- 账户、隐私和数据管理。
不要在原书知识不足时创建看似完整的预测产品。
但应在工程结构上提前考虑最终 Web/API 的集成。
安全与合规要求
面向公众时特别注意：
健康： 奇门解读不能作为诊断依据。遇到急重症迹象，应优先引导真实医疗帮助，不可让用户因算命而延误治疗。
法律与财务： 传统术数解释不能冒充专业法律或投资结论。
隐私： 用户问事可能包含姓名、关系、疾病及其他个人信息，必须保护，不应未经同意用于训练。
古籍版权： 将来公开提供全文、长段原文或商业化训练前，必须检查实际使用权与公开展示权限。保存给定文献用于项目研究，不自动意味着可以公开分发所有原文。
部署： 考虑身份认证、访问控制、备份、限流、故障处理、日志隐私、成本监控和提示词注入防护。
不允许外部用户通过聊天指令修改权威古籍资料、系统规则或模型训练数据。
未来的公众使用成本、GPU 吞吐和并发能力需要通过压测决定，不作无依据的容量承诺。

17. 多阶段研究与产品路线
我们将采用可以逐步验证的阶段计划。
Phase 0：全新项目基础工程
建立项目、数据库 schema、核心接口、Git、AGENTS.md、自动测试和跨设备开发规范。
Phase 1：《神奇之门》基础知识
我逐章提供资料。
Codex 负责完整保存、结构化、关联与规则编译。
Phase 2：确定性起盘和用神引擎
随着知识覆盖推进，逐步实现真实计算能力。
Phase 3：《神奇之门》完整案例
保存完整故事、原书盘、作者推理、具体断语、反馈和续断。
Phase 4：第一次真正的专业模型基线
先比较基础模型与加入专业知识、规则、起盘后的系统。
建立事件级冻结评估。
Phase 5：第一轮专业 SFT / LoRA
根据数据规模和 RTX 4090 实测能力选择模型。
训练重点放在专业证据组合和断案流程。
Phase 6：《开悟之门》及后续古籍
继续逐章入库，建立跨书概念和方法体系。
不断扩大高质量案例与训练数据。
Phase 7：正式问事与学习产品
完善真实 Web/API、九宫显示、对话、学习系统、用户管理及安全机制。
可以较早做小规模原型验证接口，但不能把原型视为专业完成品。
Phase 8：长期模型优化与公众产品运营
扩展更多古籍、案例及真实反馈。
系统评估专业能力、推理质量、模型成本和服务可靠性。
阶段门槛
每个阶段必须有：
- 明确交付；
- 可运行程序；
- 数据版本；
- 必要测试；
- 实际测试结果；
- 失败处理；
- 下一阶段进入条件。
不允许用版本号或漂亮报告代替真正验收。
18. 我与 Codex 的长期合作方式
我会控制文献输入顺序。
当我提供一章基础知识
你应该完成：
1. 保存不可变原文。
2. 记录出处和哈希。
3. 理解整章结构。
4. 识别知识类别。
5. 更新数据库。
6. 建立知识关联。
7. 处理重复与解释差异。
8. 编译可确定执行的规则。
9. 生成必要测试。
10. 实际运行测试。
11. 更新知识覆盖及项目进度。
完成后，简明报告结果，并准备下一章。
当我提供一个完整历史案例
你应该完成：
1. 完整保存案例。
2. 建立事件及对应盘面。
3. 保存所有原始对话。
4. 记录作者的用神选择。
5. 提取各步骤的实际证据。
6. 记录宫内和跨宫分析。
7. 记录作者综合取象和断语。
8. 记录应期与方法。
9. 区分事前断语和事后反馈。
10. 与基础规则建立来源关联。
11. 检查是否和其他古籍案例属于同一事件。
12. 按冻结数据分组要求生成训练候选。
13. 运行完整性测试。
原文没有写的内容不能猜测。
每次开发结束
应提供：
- 本次新增内容；
- 当前知识覆盖；
- 当前案例覆盖；
- 实际已编译规则；
- 运行的测试；
- 测试失败；
- 模型实验结果（如有）；
- 尚未实现的部分；
- 接下来具体要做什么。
不要仅依靠 Codex 的对话上下文保存项目状态。
19. 从以前的工程失败中吸取教训
这是一个全新项目，不允许自动导入之前的实验代码。
但必须从工程层面避免以下问题再次发生：
A. 模块写好了却没有接进主流程
解决方式：正式入口端到端集成测试。
B. 数据库明明有正确规则，模型仍凭记忆回答
解决方式：实际运行时检索、规则激活日志及模型上下文核验。
C. 用神未经条件判断就自行绑定
解决方式：结构化角色、条件匹配、规则来源和适用性校验。
D. 基础五行、宫位错误
解决方式：确定性引擎、结构化证据和最终输出事实校验。
E. 测试题只有领域和盘面，却强迫模型具体断案
解决方式：区分“信息不足测试”和“完整问事推理测试”。
F. 测试用例是多张盘，却当作一张盘评分
解决方式：多盘 ID、逐盘证据及独立校验。
G. 用模型拒绝回答制造虚假通过率
解决方式：分别计算条件识别通过率、实际断案完成率和专业正确性。
H. 输出过长或 JSON 生成失败，却被当作专业知识错误
解决方式：单独记录生成失败，改进结构化输出协议和解码方式。
I. 训练样本太少，却提前认为模型掌握了专业知识
解决方式：明确训练覆盖、优化步骤、独立验证及对照实验。
J. 一直修改版本，却没有客观进步
解决方式：固定回归集、失败案例最小复现、统一指标与版本对比。
K. 用历史案例结果泄漏到测试输入
解决方式：事件级分组、事前事后隔离、答案权限隔离。
L. 把古籍资料的真实性问题与程序复算能力混淆
解决方式：分别跟踪文献验收状态和计算校验状态。
所有这些问题必须转化为可执行的工程检查，不只是写成提醒。

21. 最终验收定义

一个完全不懂奇门的人，只要打开产品，用自然语言提出问题，系统就能在必要信息和古籍依据充分的情况下，独立完成传统奇门分析。

专业学习者能够进一步阅读原书、研究历史案例、查看作者完整断案步骤，并学习如何自己分析奇门盘。
系统必须能够扩展到约 20 本及更多古籍，并基于高质量数据和独立测试持续改进模型。
我们不要求基础模型死记所有确定性事实，因为这些应由程序保证。
我们要求模型学会如何运用知识、组织证据、进行专业综合分析。
最终的 QimenLLM 应当是一个专业知识系统、确定性计算引擎、历史断案学习系统和自然语言模型深度结合的完整产品。
